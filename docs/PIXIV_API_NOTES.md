# pixiv 搜索接口的实测机制（做全量爬取的依据）

本文记录**实测**结论，不是推测。每条都附了验证方法与数据。
做全量爬取（几十万条）时必须遵守这些规则，否则会静默漏数据。

---

## 1. 单一查询有翻页硬上限：约 6180 条 / 第 104 页

```
登录态，date_d 排序，不限定日期，逐页翻到接口不再给新内容：
  第 100 页：唯一 6000 个，本页新增 60
  ★ 第 104 页返回空列表 -> 接口到此为止
  单排序实测可达：6180 个唯一作品，翻到第 103 页
  pixiv 报告的总结果数：745200
  覆盖率：0.83%
```

注意是**返回空列表**，不是"开始重复"。所以"翻到空"就是这一查询的终点。

`--deep` 之所以有用（6180 → 10920），是因为它把「最新」和「最早」当作
**两个独立查询**，各自都有自己的 6180 额度。「最新」「最早」两个区段实测**交集为 0**。

---

## 2. `scd` / `ecd` 是**服务端**日期筛选（这是绕过上限的唯一途径）

```
基线（无日期参数）                total=745200
scd=2020-01-01 & ecd=2020-12-31  total=34094     ← 生效
scd/ecd 之外的名字（start_date、end_date、blt/bgt、dts/dte、date_from/date_to）
                                  total=745200    ← 全部无效，被忽略
```

* 参数名就是 `scd`（start）与 `ecd`（end），格式 `YYYY-MM-DD`。
* **每个时间段都有独立的 6180 额度** —— 所以把大结果集切成很多小时间段，
  每段都能被完整取完。这是"能否爬全 74 万"的关键。
* 返回结果确实被限制在区间内（实测首条/末条日期都落在请求区间里）。

⚠️ 本程序原先**完全没传这两个参数**，时间筛选是在本地对已取回的结果做的
（`DateRange.contains()`）。要做全量爬取，必须改成传服务端参数。

---

## 3. `total` 的可靠性：**跨度 ≤1 年可信，跨多年会被截断**

这是最容易踩的坑。实测（父段 vs 两个子段之和）：

```
年内区间 —— 全部完美吻合：
  2010 全年   父=41087 = 18897+22190   差   0 (0.0%)  ✓
  2015 全年   父=26137 = 12725+13412   差   0 (0.0%)  ✓
  2020 全年   父=34094 = 17100+17163   差+169 (0.5%)  ✓
  2025 全年   父=67014 = 32767+34247   差   0 (0.0%)  ✓
  2026-09     父= 5947 =  3414+ 2533   差   0 (0.0%)  ✓
  2015-06     父= 1537 =   777+  760   差   0 (0.0%)  ✓

跨多年区间 —— 全部不吻合（父段 total 被截断）：
  第 0 层  父= 68397  子=24154+ 68397= 92551   差 +35.3%  ✗
  第 1 层  父= 68397  子=36622+ 68397=105019   差 +53.5%  ✗
  第 2 层  父= 36622  子=26330+ 36622= 62952   差 +71.9%  ✗
  第 3 层  父= 26330  子=29849+ 26330= 56179   差+113.4%  ✗
```

**规律**：区间跨度 ≤ 约 1 年时 `total` 精确；跨多年时父段的 `total` 明显偏小
（看起来像"到某个较早日期为止的累计量"）。

**正确做法**：统计总量时**按自然年切块、各年各请求一次、再累加**：

```
2007:2639  2008:15057 2009:25224 2010:41087 2011:41676
2012:48430 2013:45778 2014:34335 2015:26137 2016:24837
2017:29518 2018:24513 2019:26968 2020:34094 2021:36745
2022:48857 2023:55030 2024:63269 2025:67014 2026:53234
                      按年累加 = 744,442
对照 pixiv 无日期时报告 = 745,200      ← 误差 0.1%，仅 20 次请求
```

**派生规则（重要）**：分段爬取的"要不要继续细分"判据**不能用 `total`**
（宽区间下它偏小，会导致该分的不分、最后取不全）。
应该用 **`lastPage`**，它是准的：

```
2026-09（5947 条）   lastPage=100   → 100×60 ≈ 6000  ✓
最近两天（199 条）    lastPage=4     →   4×60 ≈ 240   ✓
```

`lastPage` 的上限是 **1000**（约 6 万条）；撞到 1000 就必须继续二分。

## 4. 限流的表现与"确实没结果"无法区分（必须专门处理）

被限流时接口返回的是 **HTTP 200 + `total=0` + 空列表**，
与"这个时间段确实没有作品"**长得一模一样**。

```
基线 p=1（登录，被限流后）  total=0    条数=0
匿名 + scd/ecd 2020        total=29119  条数=60    ← 换个身份仍然正常
```

* 触发原因：短时间内发了约 500 次请求（我为了探测把间隔调到 0.12s）。
* 恢复：等待一段时间后自行解除（本次约十几分钟）。
* **如果不区分**：分段爬取会把"被限流的段"记成"该段没有作品"，
  然后**永久跳过这段数据** —— 这是最危险的失效模式。

程序里的处理（`PixivClient.search_illusts` + `RateLimited` 异常 +
`HttpClient.note_rate_limited`）：

* 连续 2 次 `total=0` + 空列表 → 抛 `RateLimited`，进入冷却并自适应降速
* 请求间隔按 2 倍递增（上限 30s），连续 50 次正常后折半回收
* 429 响应也走同一套冷却

## 5. 分段的粒度：为什么用二分而不是按月切

作品在时间上**极不均匀**：2007 年整年才 2639 个，2025 年有 67014 个
（相差 25 倍）。固定粒度切分要么切太碎（白费请求），要么切不够（漏数据）。

所以用**递归二分**，只在"这段太多"时才继续分：

```
[2007-09-01 ~ 2026-09-29]  约 1000 页  -> 细分
  [2007-09-01 ~ 2017-03-15]  ...
  [2017-03-16 ~ 2026-09-29]  约 1000 页  -> 细分
    ...
        [2007-09-01 ~ 2007-12-17]  2233 条（够小）-> 取完
        [2007-12-18 ~ 2008-04-04]  2948 条（够小）-> 取完
```

实测（2026-09-01~03，目标 300 条/段）：

```
÷ 细分 [2026-09-01 ~ 2026-09-03] 约 18 页 total=1053
÷ 细分 [2026-09-02 ~ 2026-09-03] 约 9 页  total=527
-> 最终 3 段（每天一段），收集 1053 个作品
```

**边界**：切到 1 天就不再分（`SEG_MIN_DAYS`）。若单日作品数就超过接口上限
（实测确有某天 1053 个，热门日可能上万），这一段**必然拿不全** ——
程序会明确标记 `segments_truncated` 并警告，而不是假装成功。

## 6. 段级断点续爬

全量爬取要上万次请求、几十小时。段状态记在 `_index/segments.json`：

```
实测：第一次跑 2007-09 整月 -> 完成 1 段，5 页请求，245 个作品
      第二次跑同一范围      -> 跳过 1 段，几乎 0 次请求
```

必须记在**段级**而不是"关键词+组合"级：否则中断后重跑要把整棵分段树
重走一遍（每段至少 1 次请求，上千段就是几小时）。

## 7. 成本估算（全量爬取的实际代价）

以「初音ミク」为例（按年累加 744,442 个，登录态）：

| 项目 | 估算 | 依据 |
| --- | ---: | --- |
| 搜索请求数 | 约 12,400 次 | 744442 ÷ 60 条/页 |
| 搜索耗时 | 约 3 小时 | 1.2 请求/秒（保守限速） |
| 作品平均体积 | 5.45 MB/作品 | 本机图库 169 个作品的实测均值 |
| 磁盘占用 | **约 4.0 TB** | 744442 × 5.45 MB |
| 下载耗时 | **约 200 小时** | 4 并发 × 1.5 MB/s/流 |

**磁盘是硬门槛。** 注意这是"作品平均 2.72 页"的样本，实际混合题材会偏低一些，
但量级就是 TB 级。跑之前必须确认剩余空间。

## 8. 复现这些结论的脚本

* `probe_depth.py` —— 各排序能翻多深（注意：它用共享 `seen_ids`，数字会被污染，
  只适合看单排序）
* `probe_seg.py` —— 分段是否突破上限、相邻段是否重叠
* 单排序上限的干净测量见本文第 1 节（只用一种排序，`seen` 独立）
* `test_segment.py` —— 分段收集器的回归测试（细分/去重/续爬/截断标记）
